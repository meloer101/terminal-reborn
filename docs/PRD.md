## 1. 背景与目标

### 1.1 问题
同时运行 3–10 个 Claude Code / Codex 的开发者每天都会遇到这些问题：
1. agent 的 TUI 输入框无法像正常编辑器那样选中删除，中文输入法下回车还会误发；
2. 不知道哪个 agent 正在等自己处理，常常让 agent 空等很久；
3. worktree 的创建、审阅、本地合并、冲突处理和清理分散在多个工具里；
4. 看不到“哪个分支、哪个 worktree、对应哪个 agent”的全貌；
5. 终端外观难以定制，没有一款工具能分别设置英文字体和中文字体。

每个问题都有产品做得不错，但没有一个产品把它们同时解决。

### 1.2 产品目标
在保留 agent 原生 TUI 的前提下，补齐四件事：**agent 状态与跨项目总览**、**本地 worktree 全链路**、**带 agent 状态的 git 图谱**、**可深度定制且对中文友好的外观**。（v1.2 起不做应用内输入栏。）

**定位（v1.35）**：不按功能清单追 Orca / Superset / cmux。它们跨平台、支持几十种 agent，还有手机端、SSH、GitHub / Linear 集成，而且每天发版；Wavi 补上其中任何一项，也只是“它也有”，给不了别人换过来的理由。Wavi 做小而锋利的开源产品，首批用户是**在 macOS 上同时跑多个 Claude Code / Codex 的中文开发者**：把他们每天都会碰到、大产品又排不上号的事做深。候选方向有中文输入法和 CJK 显示的正确性、中文界面和文案、国内常见的 agent 用法（第三方 API 端点、多账号、国产 agent），以及国内网络下的安装和更新。这是待验证的假设，候选方向做不做由 §1.5 收集到的证据决定。

### 1.3 成功指标

| 指标 | 目标 |
|---|---|
| “等你处理”感知延迟 | 从 hook 事件到侧栏 / 总览 + 系统通知 ≤ 1 s |
| 状态准确性 | 连续使用 1 周，状态卡死（显示错误超过 2 分钟）次数为 0 |
| 中文 | CJK 字符在终端中严格占 2 个单元格；中英文字体可分别设置 |
| 会话不丢失 | 关窗口、⌘Q、重启应用都不中断 agent；重启电脑后能接上原对话 |
| 合并闭环 | 从会话完成 → 审阅 → 本地合并 → 清理 worktree，全程不离开应用 |
| 性能 | 冷启动 ≤ 2 s；10 个活跃会话时输入延迟 < 16 ms；常驻内存 < 1.5 GB |
| 作者自用 | 作者日常完全用 Wavi 代替 Terminal / Orca（2026-10-19 基本达成，此后作者不再是需求的主要来源，见 §1.5） |
| 外部用户 | 见 §1.5 |

### 1.4 非目标（v1.0 之前不做）

## 2. 用户与核心场景

**目标用户**：在 macOS 上同时运行多个 CLI coding agent、每个 agent 各占一个 git worktree 的开发者。很多人用中英文混合写 prompt。首批用户是中文开发者（§1.2、§1.5）。

**设计原则**：终端优先，界面其余部分退后；只在需要你时打扰，“等你处理”是唯一高亮的状态；所有高频操作都能用键盘完成；用排版层级、对齐和分隔线组织信息，不靠装饰。

**Wavi 不替用户花 token**：只有用户点了按钮才向 agent 发消息，按钮写明会发什么（如“让 agent 审阅”发 `/code-review`）。可能花很多 token 的任务（如解决合并冲突）只放进输入行、不按回车，由用户看过后自己发送。不花 token 的本地检查（git 预检、端口扫描）不受此限。以后任何**自动**向 agent 发送的功能（完成后自动审阅、CI 失败自动修复、best-of-N 等）都必须在设置里有开关、**默认关闭**、写明会做什么，统一放在设置的“自动化”分组。

**核心链路**（验收标准见 §4）：

- **L1 开新会话**：⌘N → 新建会话面板（项目、工作目录、基于、智能体都已填好默认值）→ ⌘↵ → 面板关闭，侧栏立即出现该会话（正在启动）→ 选了新 worktree 时后台创建 worktree、复制被忽略文件、在终端里运行 setup → 启动 agent → 用户在终端里自己发第一句话。
- **L2 输入**：直接在终端里打字，按键原样进入 agent 的 TUI，和普通终端一样。
- **L3 被需要时**：agent 请求权限或提出问题 → 会话变为“等你处理”，总览计数、⌘J、系统通知、Dock 角标同时提示 → 进入会话，在 TUI 里作答 → agent 继续运行。
- **L4 审阅与合并**：会话完成（已完成·未读）→ 右侧“变更”查看 diff → 有问题就写行内评论发回 agent；没问题就点“合并” → 预检（是否落后基线、是否有冲突）→ 选合并方式 → 合并到基线 → 选择是否删除 worktree。
- **L5 冲突**：预检发现冲突 → 列出冲突文件 → “交给 agent 解决”（自动生成说明，放进该会话的输入行，用户按回车发送）或“中止”。
- **L6 Git 全景**：打开“图谱” → 看到 main 与所有 worktree 分支的走向、每个 worktree 的 agent 状态、领先 / 落后 → 点击节点跳到会话 → 右键合并或 rebase。
- **L7 外观定制**：⌘, → 外观 → 选主题 / 英文字体 / 中文字体 / 字号行高 → 预览实时变化。

## 3. 对象模型与状态机

```
Project（git 仓库根目录）
 └─ Worktree（branch · path · baseBranch · ahead/behind · dirty · +N −M）
     └─ Session（kind: claude | codex | shell · status · title · currentAction · startedAt · ptyId）
```

### 3.1 会话状态

| 状态 | 含义 | 进入信号（优先级从高到低） |
|---|---|---|
| `running` 运行中 | agent 正在工作 | hook `UserPromptSubmit` / `PreToolUse` / `PostToolUse`；标题出现 spinner 字符 |
| `needs_you` 等你处理 | 等待权限确认或回答提问 | hook `PermissionRequest`、`Notification(permission_prompt / elicitation_dialog)`、AskUserQuestion 对应的 `PreToolUse`；Codex 标题 `Action Required` |
| `done_unread` 已完成·未读 | 一轮对话结束，用户还没看 | hook `Stop`，且该会话当前不可见 |
| `idle` 空闲 | 已完成且已看过，或刚启动 | 用户看过 `done_unread` 的会话；`SessionStart` |
| `error` 出错 | 本轮失败 | hook `StopFailure`；进程非零退出 |
| `exited` 已退出 | 进程已结束 | PTY exit |

- `needsAttention = needs_you || error || done_unread`，总览计数、⌘J 和 Dock 角标按这个条件筛选。
- 生命周期阶段与状态并列：正在启动 / 未启动 · 点击恢复 / 被首次弹窗挡住（“等你确认：信任此文件夹”）/ 已退出 / 找不到命令。只有 PTY 退出才算终止；`SessionEnd`（如 `/clear`）之后等待下一个 `SessionStart`。
- **自愈**：hook 可能丢事件，所以定期检查进程是否存活。`running` 超过 3 分钟没有收到任何 hook 且标题显示空闲字符（Claude 为 `✳`）时降级为 `idle`；Codex 空闲标题持续 4 s 且没有 hook 时降级（§6.7）。`needs_you` 被用户在 TUI 中直接回答后（随后收到 `PostToolUse` 或 `UserPromptSubmit`），立即恢复为 `running`。
- 状态从不只靠颜色表达：每种状态都有独立的 StatusGlyph 形状和文字。

### 3.2 当前动作
由 `PreToolUse` 的 `tool_name` + `tool_input` 生成，例如 “编辑 auth.ts”、“运行 pnpm test”、“搜索 'useSession'”。没有 hook 时显示为空。

### 3.3 信息架构：两种视图看同一批会话

同一批会话有两种组织方式，各管一件事，互不混用：

| 视图 | 回答的问题 | 组织方式 | 不做的事 |
|---|---|---|---|
| **侧栏** | 它在哪？ | 严格按归属：项目 › 会话。会话永远待在所属项目下面，不会因为状态变化而移动 | 不按状态重排，不把会话提到别的分组 |
| **总览**（F9） | 现在该做什么？ | 跨项目，按状态分组：等你处理 → 出错 → 待审阅 → 运行中 → 空闲 → 已退出 | 不替代侧栏的位置导航 |

**层级规则**：子级在视觉上永远不能比父级更醒目。

| 层级 | 字号 / 字重 / 颜色 | 位置 |
|---|---|---|
| 项目（ProjectHeader） | 13px / 600 / `text-primary`（token `--text-body-heading`），左侧折叠箭头使用 `text-tertiary` | 行内边距左 8px，箭头 16px + 间距 4px |
| 会话标题（SessionRow） | 13px / 400 / `text-primary` | 缩进 28px（`--indent-tree`），状态图形正好落在项目名首字下方 |
| 会话第二行 | 12px / 400 / `text-secondary`（等你处理时用 `status-attention`） | 与标题左对齐 |
| 元信息（时长、`+N −M`、数量） | 等宽 12px / `text-tertiary` | 右对齐 |

- **Worktree 不单独占一层**：大多数 worktree 只有一个会话，所以分支名放在会话第二行（或悬停提示）里。只有同一个 worktree 下有 2 个以上会话时，才在会话之上加一行 worktree 小标题（M4 时再设计）。
- **折叠**：项目可以折叠（点项目名或箭头），折叠状态会持久保存。折叠后，项目标题行显示其下最紧急的状态图形，所以折叠项目里有“等你处理”的会话也不会被漏掉。⌘1–9 跳过折叠项目中的会话；⌘J 不受折叠影响。
- **“等你处理”的入口**：侧栏导航中的“总览”项显示需要处理的数量；⌘J 依次跳到需要处理的会话；Dock 角标和系统通知。不设置顶分组，因为它会让会话离开所属项目、在列表里跳来跳去。

### F4 Worktree 生命周期 · P1 · Figma 15（Section `170:7853`，新建会话）/ 05（Merge sheet）
- **新建会话面板**（Figma 15；取代 06 新任务）。一行一项，每项都有默认值，什么都不改直接 ⌘↵ 就能开：
  - **项目**：默认当前会话所在的项目。
  - **工作目录**：分段二选一「新 worktree / 当前目录」。按项目记住上次的选择，第一次默认新 worktree。当前目录 = 在该项目主目录里直接开，不改动 git，“基于”变灰显示当前分支（15B）。文件夹不是 git 仓库时“新 worktree”不可选，并写明原因（15F）。
  - **基于**：分支下拉，默认项目默认分支，创建前先 `git fetch`。下拉里可搜索，分本地分支 / 远程分支两组；已经在某个 worktree 里检出的分支标“已在 worktree 里”，选它就改为在那个 worktree 里再开一个会话（git 一个分支只能在一个 worktree 里检出）（15C）。
  - **智能体**：Claude Code / Codex / 终端。
  - **高级**（默认收起，收起时显示分支名）：分支名（自动生成 `<前缀>/<两个词>`，如 `jacob/swift-otter`，可改）· 文件夹（`~/.tr/worktrees/<repo>/<name>`，存放位置在设置里改）· 准备（复制 `.worktreeinclude` 列出的文件 + 运行 setup，开关）（15D）。分支名已存在时输入框标红、写明原因，“创建”不可点（15E）。
  - **不写任务描述**：创建后直接进入会话，用户在终端里自己发第一句话。面板里只在出错或有限制时显示说明文字，平时不加解释。
- **入口**：⌘N 和项目标题的 ＋ 打开面板（＋ 预选那个项目；还没有项目时 ⌘N 先打开项目）。会话右键和 Worktree 视图的“在此新建会话”不弹面板，直接在那个 worktree 里再开一个会话。
- 点“创建”后面板立即关闭，侧栏马上出现该会话。新 worktree 的后台执行：`git fetch` → `git worktree add --no-track -b <branch> ~/.tr/worktrees/<repo>/<name> <base>` → 记录 `branch.<name>.base` → 按 `.worktreeinclude` 用 `cp -c`（APFS 写时复制）复制被忽略文件 → 在可见终端里运行 setup 脚本 → 启动 agent（不送 prompt）。
- **脚本与端口**：可以提交进仓库的 `.tr/settings.toml`，配置 `setup`、`run`、`archive` 和可选的 `test`；会话头放一个 Run 按钮；按工作区分配端口段，注入 `TR_PORT`。起点在设置 · Worktree（默认 41000）；Worktree 详情显示分到的端口段。
  ```toml
  [scripts]
  setup = ["npm ci", "cp .env.example .env"]   # 新 worktree 的终端里、agent 之前
  run = "npm run dev -- --port $TR_PORT"         # 会话头 ▶，单独的 run 终端
  test = "pnpm test"                             # 合并前；失败则不能合并
  archive = "docker compose down"                # 归档时（F15）
  ```
  仓库的脚本是仓库里的代码：第一次运行、以及内容改变后都先弹确认框列出全部命令（细节见 v1.26、v1.28）。没有 `test` 时不跑测试、也不因此重新确认。
- 本地合并：预检（落后基线的提交数、`git merge-tree --write-tree` 冲突检测、可选测试命令）→ 选择 merge `--no-ff` / squash / rebase + `--ff-only` → 可选“合并后删除 worktree（保留分支）”和“推送到 origin”。
- 冲突处理：列出冲突文件和原因 →「交给 agent 解决」会自动生成说明（冲突类型、分支、文件列表、提醒设置 `GIT_EDITOR=true`），放进该会话的输入行、不按回车（§2 不替用户花 token）；或者选择「中止」。能识别仓库处于 merge / rebase / cherry-pick 进行中的状态。
- 清理：合并后提示删除；列出孤儿 worktree（P2：按 TTL 自动回收）。
- **验收**：在测试仓库上完成 L1 / L4 / L5 全流程；合并失败时仓库能回到干净状态。

### F5 Diff 审阅 · P1 · Figma 03（Panel · 变更）/ 13B / 17F–H（并排）
- 右侧栏 Git 页签的“变更”视图（F17）：对比基线的文件列表、汇总 `+N −M`，支持统一 / 并排两种布局（自研，只渲染可见行）。
- **并排**（Figma 17F / 17G / 17H）：视图行最右边的分段「统一 / 并排」，只在“变更”里出现。右侧栏宽 ≥ 720 才能并排；更窄时“并排”置灰，悬停提示“右侧栏宽 720 以上才能并排”，diff 回退到统一，用户的选择保存在 workspace.json，拉宽后自动回到并排。左 = 基线，右 = 新；一段改动里第 i 行删除和第 i 行新增配成一行，对面没有对应行时那一半用 `bg/hover` 填空；上下文行两边都有、各带行号；hunk 头横跨两栏。悬停 ＋ 和行内评论只挂在右边（新）；评论和编辑框画在右半边，左半边填空。统一视图里写在删除行上的旧评论在并排里仍显示在那一行下面。⇧ 点击扩范围、窗口化渲染和评论流程不变。
- 行内评论：悬停 diff 行出现 ＋，点它在该行下面写评论，⇧ 点击另一行扩成多行范围；可以在多个文件里写多条，保存在 workspace.json，直到发送或放弃。多条评论按文件、行号合成一条 prompt（位置 + 引用的代码 + 意见），放进该 worktree agent 会话的输入行，由用户按回车发送（§2）。
- 底部操作：有评论时为 发给 Claude · N · 放弃 · 合并到 main；没有评论时为 让 agent 审阅（F13）· 创建 PR · 合并到 main。
- **验收**：Figma 03 还原；1 万行 diff 滚动流畅。

### F6 Git 图谱 · P1 · Figma 04（Panel · 图谱）
- 自研 lane 算法（`src/shared/git-graph/lanes.ts`，O(n·lanes)，支持增量分页，每页 200 个提交）；默认分支（main / master / origin/HEAD，再退到 origin/main / master）固定在第 0 列；分支结束后右侧的 lane 在同一行里斜移收拢，线的颜色跟着 lane 走；文字列按第一页的宽度对齐；每行用 SVG 绘制，行高固定，只渲染可见的行；refs 变化时按已加载的数量整体重载并保持滚动位置。实测（5001 个提交、无 commit-graph 文件）：打开 Git 视图到首屏 75–111 ms，滚到最早的提交约 2 s。
- 在提交行上标出每个 worktree 的 HEAD，以及对应 agent 的 StatusGlyph，点击跳到该会话。
- 筛选：全部分支（本地 + 远程分支、tag、各 worktree 的 HEAD；不含 stash）/ 仅 worktree（只看各 worktree HEAD 能到达的提交）；另有“隐藏远程分支”开关，给有大量 `origin/*` 的仓库用。
- 右键菜单：切换到会话 · 合并到基线 · 基于基线 rebase · 复制 SHA · 新建 worktree · 删除 worktree。
- 图谱是右侧栏 Git 视图的默认内容（F17，Figma 13B）；原先图谱下方的 Worktree 列表移到 Worktree 视图。
- **验收**：Figma 04 还原；5000 个提交的仓库首屏 < 300 ms。

### F7 外观 · P0（主题 token）/ P1（设置页）· Figma 07 / 08
- 深色和浅色两套主题，token 来自 Figma 变量（Color：bg / text / border / status / diff / term / lane；Layout：space / radius），导出为 CSS 变量。
- **英文字体和中文字体分别设置**：xterm 的 `fontFamily` 为 `"<英文>", "<中文>", monospace`，开启 `rescaleOverlappingGlyphs`；字体加载完成后执行 `clearTextureAtlas()`。
- 字号、行高（默认 1，与普通终端一致）、连字；侧栏毛玻璃（`vibrancy: 'sidebar'`，终端区域保持不透明）。

- 设置页右侧实时预览；P2 支持导入 Ghostty / iTerm 主题。
- **验收**：Figma 07 / 08 还原；修改设置后，所有终端在 100 ms 内生效，且不需要重启会话。

### F9 状态总览 · P0 · Figma 11 v2（Section `106:3639`）
用户在一个页面里分诊所有 agent，不需要逐个切换会话（Claude Code agent view、Superset Workspaces、Conductor、Vibe Kanban 等产品都采用这一形态）。
- **入口**：主区的一个视图，与终端互斥，不是弹窗。打开方式：侧栏“总览”或 ⌘⇧A；Esc 或 Enter 进入会话后回到终端。
- **列表（默认）**：跨项目按状态分组，顺序为 等你处理 → 出错 → 待审阅（`done_unread`）→ 运行中 → 空闲 → 已退出。已退出组默认折叠；分组的折叠状态会保存。**列表里没有分隔线**：分组只靠留白和字号区分——分组标题高 32，12/500 次要色文字 + 数量，不用色块、不画线；会话行高 40，行内所有文字行高 20、严格垂直居中；分组之间用 16 的间距隔开。没有会话的分组在列表里不显示（看板仍保留每一列）。

## 6. 技术架构

### 6.1 进程模型
```
Main（Electron 主进程）
 ├─ 工作区、设置、窗口状态：原子写入的 JSON（~/Library/Application Support/Wavi；`npm run dev` 用 Wavi Dev）
 ├─ HookBridge：规范化 hook 事件 → 状态机 → 通过 IPC 推送给 renderer
 ├─ GitService：调用 git CLI 子进程（不用 libgit2）
 └─ WorktreeService / Notifications / Dock badge
tr-ptyd（PTY 守护进程，独立于应用存活，§6.8）：node-pty 会话池 · 每会话一个 HeadlessMirror · hook socket
PtyHost（utilityProcess）：守护进程不可用时的后备，会话随应用结束
Renderer（React 19 + zustand）：侧栏 · 总览 · TerminalSurface(xterm.js) · 右侧面板 · 设置
```

### 6.2 Hooks 注入（不修改用户的全局配置）
- 应用自己拼 agent 的启动参数，不用 wrapper：Claude 用一个 `--settings <生成的 json>`（只能有一个，§6.6）；Codex 用 `-c hooks.<Event>=…` 加 `-c hooks.state=…` 固定信任（§6.7）。从不写 `~/.claude/settings.json` 或 `~/.codex/*`。
- hook 命令是 `/bin/sh '<tr-hook.sh>' <Event> <agent>`：读取 stdin 的 JSON，用 `curl --unix-socket` 带上 `TR_SESSION_ID` 和 `X-TR-Token` 发给 hook socket；应用不可达时 exit 0、不输出。PTY 环境里的 `TR_SESSION_ID / TR_HOOK_SOCK / TR_HOOK_TOKEN` 由 main 设置，覆盖 renderer 传来的同名变量。
- 服务端拒绝没有 token 的请求（403）和不是自己启动的 PTY 的请求（404）。只转发规范化后的事件，从不转发原始 payload。
- Codex 启动时用 `-c check_for_update_on_startup=false` 和按次的 `projects` 信任跳过启动弹窗。Claude 的目录信任框不预写，检测到时把会话标为“等你确认：信任此文件夹”。
- 同一个 `--settings` 文件里还有 statusLine（F11），它替换而不是合并用户的 statusLine，所以中继脚本串联用户自己的：PTY 环境里的 `TR_USER_STATUSLINE` 由 main 按会话目录解析（只读）。守护进程补放的 hook 日志里 StatusLine 只留最新一条。
- 待做：用户自己在 alias 里追加的 `--settings` 需要和我们的深合并成一个。

### 6.3 终端
- 定义 `TerminalSurface` 接口（write / onData / buffer 读取 / OSC 订阅 / resize），xterm.js 是它的第一个实现，以后可以替换为 libghostty。
- xterm 配置：使用 WebGL 渲染，失败时**按终端**回退到 DOM 渲染；开启 unicode11；字形图集不让它合并（见下一条）；kitty 键盘协议保持关闭；切换标签或面板后强制执行 fit + resize。
- 实测结论 · WebGL 字形图集（addon-webgl 0.19.0，2026-10-20）：图集长到 16 页开始合并页时，GPU 会取错纹理，中文出现叠字、错字和缺字，缓冲区内容本身是对的；原地清空图集修不好。做法（`atlas-guard.ts`）：图集长到 12 页时，等这一帧画完就重建 WebGL 渲染器、换一个新图集，所以永远不会合并；重建后紧接着那一帧又把图集填满的终端改用 DOM，下次显示时再试 WebGL（沿用 WebGL 丢失的处理）。代价是每次重建卡一帧（80–110 ms），并且依赖 addon 的一个内部字段（图集页数）。上游修复 xterm.js#5883 在 7.0.0，正式版发布后升级并删掉这层保护。压测：`TR_STRESS=1 npx playwright test e2e/webgl-cjk-stress.spec.ts`。
- 行高默认 1；终端底色取主题色（F7）。

### 6.6 实测结论 · Claude Code hooks（2.1.299，2026-10-14）
脚本 `scripts/spikes/30-hooks-lab.mjs`；真实 payload 在 `src/main/hooks/fixtures.ts`。
- **`--settings` 是合并，不是替换**：用户自己的 hooks、插件 hooks 和我们的 hooks 对同一事件都会运行；用户的 permissions / model 不受影响。**传两个 `--settings` 时只认最后一个**，第一个整个被丢掉，所以命令行上只能有一个。
- hook 命令是 shell 字符串；脚本丢了执行位会以 126 失败，所以用 `/bin/sh '<script>'` 调用。路径里的空格（`Application Support`）要加引号。
- **目录信任之前 hooks 不运行**（连 SessionStart 都没有），所以“还没收到 hook”按未知处理，不算出错。
- 与 Orca 等工具的全局 hooks 并行运行、互不影响：它们没有 `TR_*` 环境变量，我们的 hook 在它们的终端里不起作用，反之亦然；Orca 对 PermissionRequest 返回的 `{}` 不会盖掉我们的决定。
- **“等你处理”以 PermissionRequest 为准**：`Notification(permission_prompt)` 要晚约 6 s；`idle_prompt` 在 Stop 后约 60 s。
- **AskUserQuestion 也会触发一个不带 suggestions 的 PermissionRequest**，它不是允许 / 拒绝问题，要立即空回复；问题内容取自 PreToolUse 的 `tool_input`。
- PermissionRequest 没有 `tool_use_id`，靠“工具名 + 输入”和后面的 PostToolUse 配对。
- 挂起 PermissionRequest 时，TUI 自己的确认框照常显示；用户在 TUI 里作答后，Claude **不会**结束 hook 进程，要由我们回空结果释放。空结果 = 没有意见，TUI 照常。v1.2 起一律立即空回复（`holdPermissions: false`）。
- 当时“总是允许”的实测：原样返回 suggestions 里的 `setMode` 会切换整个会话的模式；`destination: userSettings` 会写 `~/.claude/settings.json`。以后如果再做应用内允许，这两类必须过滤掉。
- 用户默认的 auto 模式下，无害的 Bash 不会触发 PermissionRequest。
- PostToolUse 带完整的工具输出（可能几 MB），服务端上限 32 MB。
- 延迟：每个 hook 15–25 ms（SessionStart 冷启动约 75 ms）；UserPromptSubmit 在回车写入约 75 ms 后到达。`SessionEnd` 的 hooks 一共只有 1.5 s。
- **statusLine 与 todo 工具**（2.1.301 实测，2026-10-16；2.1.303 二进制核对，2026-10-19）：statusLine 命令的 stdin 有 `context_window`（`used_percentage` 0–100，第一次 API 响应之前是 null；`context_window_size`；`current_usage` 的 input / cache_creation / cache_read）和 `rate_limits.five_hour / seven_day`（`used_percentage`、`resets_at` 为**秒**；API key 登录和第一次响应之前没有这个字段）。轮次进行中约 1–2 s 调一次，空闲时不调。`--settings` 里的 statusLine 是**整个替换**（不是像 hooks 那样合并），所以中继脚本串联用户自己的 statusLine：同一份 stdin 交给 `$TR_USER_STATUSLINE`，原样打印它的输出（已验证）。todo 工具：`TaskCreate { subject }` → 响应 `{ task: { id } }`、`TaskUpdate { taskId, status }`（`deleted` 为删除）、`TodoWrite { todos: [{ content, status, activeForm }] }`（整表）；都不触发 PermissionRequest。对 Claude 5 模型默认**关闭**（只对旧模型、非交互模式或 `CLAUDE_CODE_ENABLE_TODO_TOOLS=true` 打开，`CLAUDE_CODE_ENABLE_TASKS=false` 时用 TodoWrite），2.1.303 未变。脚本 `scripts/spikes/31-statusline-todo-lab.mjs`（在 `claude/ctx-todo-ports` 分支）。statusLine 还带 `model.display_name`、`cost.total_cost_usd`、`context_window.total_output_tokens`（文档里另有 `prompt_cache` 的 `warm` / `expires_at`，本机版本未见，读不到就不显示）。
- **context 百分比与自动压缩点**（2.1.304 二进制核对，2026-10-20）：statusLine 的 `used_percentage` = round((input + cache_creation + cache_read) / `context_window_size` × 100)，不含输出，分母是完整窗口；`/compact` 之后到下一次响应 `current_usage` 和 `used_percentage` 都是 null。Claude 自己的压缩点：有效窗口 = `autoCompactWindow`（设置 / `CLAUDE_CODE_AUTO_COMPACT_WINDOW`，否则模型窗口；服务端实验也可能改）− min(maxOutputTokens, 20000)，阈值 = 有效窗口 − 13000（`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 可再降），即 200k → 167k、1M → 967k；阈值前 20k 开始提示，提示里的 token 数含上一次输出。statusLine 不给这个阈值，Wavi 按同一公式和自己的环境变量算（用户 settings 里的 `autoCompactWindow` 和服务端实验看不到）。
- **账号额度 `get_usage`**（2.1.304，2026-10-20，标着实验性）：`claude -p --input-format stream-json --output-format stream-json --verbose` 下先发 `{"type":"control_request","request_id":…,"request":{"subtype":"initialize"}}`，再发 `{"subtype":"get_usage","skip_behaviors":true}`，回 `control_response`：`subscription_type`、`rate_limits_available`、`rate_limits.five_hour / seven_day / seven_day_opus / seven_day_sonnet`（`utilization` 0–100、`resets_at` ISO）和更新的 `rate_limits.limits[]`（`kind` session / weekly_all / weekly_scoped，`group`，`percent`，`resets_at`，`scope.model.display_name`，本机有 `Fable`）。不发模型请求；数据同 `/usage`（内部调 `api.anthropic.com/api/oauth/usage`，Claude 自己缓存 60 s、记 429）。默认会跑用户和插件的 SessionStart hooks，所以加 `--setting-sources ''`、`--settings '{"disableAllHooks":true}'`、`--strict-mcp-config --mcp-config '{"mcpServers":{}}'`、`--no-session-persistence`、`--disable-slash-commands`：这样 hooks 不跑、不写会话，约 1.2 s 答完；登录仍可用（`--bare` 不行，它不读 OAuth）。实测同一时刻 statusLine 存的是 5h 3%，`get_usage` 是 20%。
- **不改全局配置时能怎样把设置交给手动启动的 Claude**（2.1.303 二进制核对，2026-10-19）：只有命令行 `--settings`（只认最后一个）；没有“额外设置文件”的环境变量。`CLAUDE_CODE_MANAGED_SETTINGS_PATH` 会让 Claude 改读这个目录作为策略设置、不再读本机的 managed-settings，等于绕过管理员策略，不用。所以用 PATH 上的 shim 补 `--settings`（cmux 同样做法）。本机用户的 zsh 配置实测：`whence -a claude` 第一个是 shim，`~/.local/bin/claude` 在后，ZDOTDIR 被放回。
- **transcript 里的用量**（2.1.299 本机 transcript，2026-10-19）：每条 assistant 消息的 `message.usage`（`input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens`、`output_tokens`）；同一条消息按内容块写成多行、`message.id` 相同，按 id 只算一次（后一行 output 更大时补差）；`isSidechain: true` 是子 agent，算花费不算 context；用户输入是 `type: user` 且 `message.content` 为字符串或含 text 块（`tool_result`、`isMeta`、`isCompactSummary` 不算一轮）；压缩是 `type: system, subtype: compact_boundary`（带 `compactMetadata.preTokens`）。每行有 ISO `timestamp`。
- **会话标题**（2.1.302，2026-10-18，`30-hooks-lab.mjs title`）：hook payload 里**没有**标题字段，只有 `transcript_path`。Claude 在第一条 prompt 后约 4 s、和回复并行，用小模型生成标题，写进 transcript：`{"type":"ai-title","aiTitle":"…"}`；/rename 写 `{"type":"custom-title","customTitle":"…"}`，显示规则是 `customTitle ?? aiTitle`。两种条目每一轮都会在文件尾部重新追加一遍，所以只读文件尾部（4 MB）就够。标题之后不会随对话变化。本机 80 个会话里 74 个在第一条回复之前就有了 ai-title。Wavi 在 SessionStart（含 --resume）、Stop 时读，第一条 prompt 后 3 / 8 / 20 s 再读；只接受 `~/.claude/projects`（或 `$CLAUDE_CONFIG_DIR/projects`）下的 `.jsonl`。

### 6.7 实测结论 · Codex（0.142.5，2026-10-14）
脚本 `scripts/spikes/40-codex-hooks-list.mjs`、`41-codex-hooks-lab.mjs`、`codex-mock-provider.mjs`（本地模拟模型）；payload 在 `src/main/hooks/codex-fixtures.ts`。当时第三方模型服务一直返回 503，所以依赖真实模型的行为没有验证。
- hooks 默认开启，0.142.5 认 10 个事件。**没有 SessionEnd 和 Interrupt**（未知事件名会被静默丢掉）；也没有 PostToolUseFailure、Notification、StopFailure。**SessionStart 在第一条 prompt 时才发**。失败的请求和被中断的回合**不发 Stop**。
- **注入**：`-c hooks.<Event>=[{hooks=[{type="command",command="…",timeout=N}]}]` 形成独立的 `sessionFlags` 层，和用户的 hooks 叠加。换 `CODEX_HOME` 会丢掉登录状态，只在 e2e 里用。
- **信任**：会话级 hook 默认 untrusted，会被跳过。不用 `--dangerously-bypass-hook-trust`，因为它会放行仓库和插件里所有没审过的 hook。做法：每次运行应用时启动一次 `codex app-server`，用 `hooks/list` 读出我们这些 hook 的 `currentHash`（0.3–0.5 s，失败不缓存），再用 `-c hooks.state={"<key>"={trusted_hash="sha256:…"}}` 只信任这几条。hash 由 Codex 自己算，我们不重新实现。探测失败或没覆盖全部 6 个事件时，就不带 hooks 启动，只靠标题判断状态。
- **PermissionRequest 挂起时 Codex 不显示自己的确认框**（与 Claude 相反）。allow 会运行工具；deny 让工具失败，但回合继续；空回复后 Codex 才显示原生确认框。`updatedInput` / `updatedPermissions` / `interrupt` 对 Codex 会“fail closed”，所以决定里只写 `behavior`。
- 原生确认框：`y` / `1` 允许；`Esc` / `3` 取消并中断整个回合；`p` / `a`（不再询问）会写 `~/.codex/rules`，应用永远不发。
- `request_user_input` 只在 Plan 模式出现，不触发 PermissionRequest；按数字选中即提交，最后一题提交整个调用，没有确认页。
- **标题**：空闲时是目录名；工作中（包括 PermissionRequest 挂起时）是盲文 spinner + 目录名；原生确认框出现时 `[ ! ] Action Required | <dir>` 和 `[ . ] …` 交替。状态规则：Action Required → `needs_you`；空闲标题持续 4 s 且没有 hook → `idle`（覆盖中断、503 这些没有 Stop 的情况）。不发 OSC 9 / 777 / 133 / 7501。
- 空 prompt 下按一次 Ctrl+C 就开始退出；运行中 Ctrl+C 和 Esc 都只是中断回合。
- 工具映射到 Claude 的词汇：shell → `Bash {command}`；`apply_patch` → `Write` / `Edit`；`request_user_input` → `AskUserQuestion`。PostToolUse 的 `tool_response` 是纯字符串，没有退出码。
- 延迟：UserPromptSubmit 在回车约 100 ms 后到达，PermissionRequest 比 PreToolUse 晚约 21 ms。
- **上下文与额度**（2026-10-19，`scripts/spikes/42-codex-usage-lab.mjs` + 本地模拟模型发 `x-codex-primary-used-percent / -window-minutes / -reset-at` 和 `secondary` 同名响应头）：每次模型响应后 rollout 追加一行 `{"type":"event_msg","payload":{"type":"token_count","info":{"last_token_usage":{"total_tokens":…},"model_context_window":258400,…},"rate_limits":{"limit_id":"codex","primary":{"used_percent":40.5,"window_minutes":300,"resets_at":<秒>},"secondary":{"used_percent":12,"window_minutes":10080,"resets_at":<秒>},…}}}`。没有这些响应头时（API key、第三方服务商，本机历史 rollout 全部如此）`primary` / `secondary` 是 null，只能显示上下文；第一次响应之前 `info` 是 null。**所有 hook payload 的 `transcript_path` 就是这个 rollout 文件**（SessionStart / UserPromptSubmit / Stop 实测）。rollout 由 Codex 的写线程追加，hook 之后 0.3 s / 2 s 各读一次尾部（512 KB）。上下文百分比照 Codex TUI 的“% context left”：窗口和已用都先扣 12,000 基线。真实 ChatGPT 账号的响应头没有在本机验证（服务商 503）。**主动问账号**（2026-10-20，0.142.5 本机 + openai/codex 源码）：`codex -s read-only -a never -c features.plugins=false app-server`，`initialize` → `initialized` → `account/rateLimits/read`，回 `{ rateLimits, rateLimitsByLimitId: { codex: { primary / secondary: { usedPercent（整数）, windowDurationMins, resetsAt（秒） } } } }`，另有 `account/rateLimits/updated` 推送；不开线程、不发模型请求。0.142.5 的这个方法**不收参数**（传 `{excludeResetCreditDetails:true}` 报 “expected unit”，传 `{}` 可以），新版收 `excludeResetCreditDetails`；API key 登录回 `chatgpt authentication required to read rate limits`（本机即如此，所以本机看不到 Codex 额度）。rollout 的 `rate_limits` 可能是按模型的另一组（`limit_id` 如 `codex_bengalfox`），只认 `codex`。自动压缩：`model_context_window` 已是模型窗口 × `effective_context_window_percent`（默认 95，272k → 258.4k），压缩点 = 模型窗口的 90%（`model_auto_compact_token_limit` 更低时取它），272k → 244.8k，在 TUI 的刻度上约 94%。transcript-meter 用同一个文件算每轮的 context 和花费：`token_count` 里 `total_token_usage.total_tokens`（累计）变大才算新花费（只更新额度时会重复写一行），花费 = `last_token_usage` 的 `input_tokens − cached_input_tokens + output_tokens`；`event_msg / user_message` 是一轮的开始，顶层 `type: compacted` 是压缩（0.142.5 本机 rollout 核对了前两种）。
- **会话标题**（2026-10-18，`41-codex-hooks-lab.mjs title` + 本地模拟模型）：0.142.5 的 TUI 不会自动起名，只有 Codex 桌面版会。**0.163.0** 的 TUI 在第一轮 Stop 后约 60 ms 发一个结构化输出请求（`{title}`，≤ 36 字，用用户的语言）；没登录 ChatGPT 时发给会话当前的模型服务商。结果追加到 `$CODEX_HOME/session_index.jsonl`：`{"id":<session_id>,"thread_name":"…","updated_at":"…"}`，**`id` 就是 hook payload 里的 `session_id`**；同一 id 以最后一行为准（改名会再追加一行）。终端标题同时变成 `<标题> | <目录>`，不以 spinner 开头，状态规则照常按空闲处理。Hook payload 里没有标题字段。Wavi 在 Stop 后 0 / 2 / 6 / 15 / 30 s、SessionStart 和 UserPromptSubmit 时读这个文件，只读不写。用户的模型服务商不可用时（本机第三方服务一直 503）就没有标题，保留首条 prompt。注意：0.163 第一次启动会弹“Meet GPT-6 Sol”，并在 `~/.codex/config.toml` 的 `[tui.model_availability_nux]` 里给计数加一，这是 Codex 自己的行为。

### 6.8 PTY 守护进程（2026-10-16 实现）
参考 Orca（MIT）的 `src/main/daemon/*`，只取核心形态，不要 launchd。e2e：`e2e/pty-daemon.spec.ts`；其余 e2e 用 `TR_KILL_SESSIONS_ON_QUIT=1` 退出，不留守护进程。
- **进程**：应用自己的二进制以 `ELECTRON_RUN_AS_NODE=1` 运行 `out/main/pty-daemon.js`，detached、独立会话，cwd 为 userData（不能是可能被删的 worktree）。依赖 Electron 的 `runAsNode` fuse 保持开启。应用退出、main 崩溃、开发时 ⌘R 都不影响它。
- **端点**：`<userData>/daemon/` 下有 `daemon-v<PROTOCOL>.sock`（路径超过 103 字节时改用 `/tmp/tr-<uid>-ptyd-<hash>/`）、`token`（32 字节）、`daemon.json`（pid、协议、版本）、`daemon.log`（5 MB 轮转）。目录 0700、文件 0600，拒绝符号链接。每个连接的第一帧是 `hello {token, protocol}`，用 `timingSafeEqual` 比较。
- **启动**：能连上就接管；`ENOENT` / `ECONNREFUSED` 就删掉旧 socket、拉起新的，3 s 内轮询连接；其他错误（超时、`EPERM`）不当作“已死”，本次退回 utilityProcess（`TR_PTY_DAEMON=0` 可强制）。运行中连接断开，按终端进程崩溃处理（恢复卡片 + `--resume`）。
- **协议**：NDJSON；在原有 HostRequest / HostEvent 之外加 `hello` / `list` / `attach` / `detach` / `shutdown`，`data` 事件带 `seq`。spawn 使用**应用**当前的环境变量，避免几天前启动的守护进程给新 shell 一个过期的 PATH。`hello` / `list` / `shutdown` 跨版本冻结：协议版本不同时，旧守护进程的会话存盘、结束，再用 `--resume` 冷恢复。
- **HeadlessMirror**：每个会话一个 `@xterm/headless`（scrollback ≤ 5000、unicode11）。快照 = 序列化的屏幕（含备用屏）+ 重放模式序列（备用屏、bracketed paste、应用光标、隐藏光标、焦点上报、鼠标跟踪和 SGR 编码）+ 最后的标题。用一次空写入的回调取得和 `seq` 一致的切点。没有客户端时不暂停 PTY，agent 不会因为应用关着而卡住。
- **重连**：每次页面加载只调用一次 `pty.live()`（第二次会把本页会话悄悄 detach），然后 attach 所有活着的会话（状态、通知需要它们的输出）。渲染端清屏 → 按快照尺寸 → 写快照、模式、标题 → 丢掉 `seq` 不超过快照的数据块 → 进入实时。没命中就走冷路径：先画磁盘快照，再 `--resume`。窗口卸载和渲染进程崩溃只 detach，不 kill。
- **退出**：⌘Q 不确认，会话继续；⌥⌘Q 结束所有会话。没有活会话、也没有客户端 10 s 后守护进程退出；拉起后 2 分钟没被接管也退出。已退出的会话保留退出码和最后一屏。
- **hooks**：守护进程持有 hook socket（`<userData>/daemon/hooks/`），收到的事件转给 main 的 HookBridge。应用没连着时立即空回复，并记入该会话最近 64 条日志（超过 64 KB 的 payload 置空）；重连时按原时间戳补放，所以关着应用时结束的回合，打开后显示正确的状态。
- **磁盘快照**：没有客户端时，会话安静 30 s 后由守护进程写 `terminal-snapshots/<id>.json`（与渲染端同格式、同 2 MB 上限），这样重启电脑后冷路径也能看到最新一屏。同一时间只有一个写者。
- **实测**（打包版 arm64，Claude 2.1.302）：守护进程启动约 145 ms；⌘Q 后应用 0.2–0.3 s 退出，shell、claude、守护进程都还在；重开后是同一组 pid，第一帧 68–140 ms（目标 < 150 ms）；真实 agent 下守护进程 CPU < 1%。纯吞吐（`seq 1 3000000`）时瓶颈在 PTY 读取，和 utilityProcess 相当。

### 6.9 实测结论 · 向 TUI 写入文字和按键（Claude 2.1.296–2.1.299 / Codex 0.142.5）
规划在 `src/shared/send-protocol.ts`；脚本 `scripts/spikes/harness.mjs`、`22-ask-user-question.mjs`。
- 每个 PTY 一个串行发送队列。正文用 `ESC[200~ … ESC[201~` 包起来写入，先清除会提前结束粘贴的控制字符；在 xterm buffer 里看到正文开头或占位符后才进入下一步，超时按 UTF-8 字节数计算。
- 回车 `\r` 单独写一次（Claude 等 60 ms，Codex 等 150 ms）。
- 占位符阈值：Claude 超过 800 字符或含 3 个以上换行；Codex 超过 1000 字符。
- `/` 命令首字符单独按键；Claude 里长到会变成占位符的 `/cmd` 必须逐字输入，否则不再被识别为命令；Codex 不带参数的 slash 命令末尾补空格，防止误执行模糊匹配项。`#` 不用特殊处理。
- agent 正忙时发送 = **排队**（Claude 依次处理；Codex 会把多条合并），不是打断。
- Claude 的 AskUserQuestion 菜单：选项编号后面固定跟 `Type something`（N+1）和 `Chat about this`（N+2）。单选按 `N` 直接提交；自由文本按 `N+1`、输入、`Enter`；多个问题时每题答完自动进下一题，最后在“Review your answers”再按一次 `Enter`；多选按 `N` 切换，`→` 离开；多选加自由文本要用 `↓` 移到对应行输入。超过 9 个选项时用方向键加 `Enter`。

### 6.10 实测结论 · 后台审阅（Claude Code 2.1.302，2026-10-18）
同一个 3 行 diff（一个真 bug、一个边界问题），`claude -p --model haiku --output-format json --json-schema <schema> --no-session-persistence`：
- 继承用户全部配置（插件、skill、MCP）：27 s、$1.25，计划模式下 `Bash(git diff:*)` 被拒，审的是文件而不是 diff。
- diff 由调用方放进提示词，`--permission-mode plan --tools Read,Grep,Glob --strict-mcp-config --setting-sources project,local`：**11 s、$0.039**，两个问题都找到，`structured_output` 完整。结论：后台审阅必须由 Wavi 控制上下文。
- `--bare` 只认 `ANTHROPIC_API_KEY` / apiKeyHelper，订阅登录用不了；`--safe-mode` 会连 CLAUDE.md 一起关掉。都不用。
- 返回 JSON 里有 `total_cost_usd`、`duration_ms`，可以直接显示。
- **项目规范仍会加载**（2026-10-19，Claude Code 2.1.303）。`--setting-sources project,local`：0 个 skill，不加载用户插件，debug 里没有用户 MCP 连接，也没有 `project memory is off`。对照：`--setting-sources user` 和 `--safe-mode` 都会打出 `$.fs.ancestors (cc-plugin-agents-md): project memory is off`（祖先目录的 AGENTS.md 被关掉），并加载 72 个 skill（用户 50 个）和 25 个插件。2.1.303 客户端里，project 对应 `CLAUDE.md`、`.claude/CLAUDE.md`、`.claude/rules` 和祖先 `AGENTS.md` / `.claude/AGENTS.md`，local 对应 `CLAUDE.local.md`，user 对应 `~/.claude/CLAUDE.md`。审阅继续用 `project,local`。订阅账号当时冻结（`Your account is on hold`，花费 0），模型没有把规范原文复述回来。
- **规范文件的大小**（同一客户端，默认 20 万 token 窗口）：每个文件 40,000 字符，全部规范合计 120,000 字符。diff 放在用户消息里，不占这份额度。
- **Claude 的大提示**。审阅参数（`--setting-sources project,local --strict-mcp-config`）下，用户提示 2,900,000 字符仍会发到认证，约 4–5 秒后返回账号冻结；2,950,000、3,000,000、3,050,000、4,000,000 字符在约 4.2 秒本地返回 `Prompt is too long`，请求没发出去，花费 0。阈值随系统提示变长而前移。模型窗口上的拒绝（客户端说明里是接近 20 万 token 时 `Prompt is too long · automatic compaction failed`）这次没测到，冻结发生在那之前。自动压缩会把 diff 摘要掉，审阅不用。
- **Codex `--output-schema`**（0.142.5）。`codex exec --ephemeral --json --output-schema <file> -o <file>` 的 Responses 请求带 `stream: true`，以及 `text.format = { type: "json_schema", strict: true, name: "codex_output_schema", schema }`。本地模拟模型按 schema 回 `{"findings":[…]}` 时退出码 0，`-o` 和 JSONL 里 `agent_message.text` 都是这段 JSON。0.142.5 不检查返回是否符合 schema：回 `{"title":…}` 或一段纯文本也是退出码 0，原样写入 `-o`，所以 Wavi 自己解析，失败就标这次审阅失败。`--sandbox read-only` 仍会在请求里带上 `exec_command`、`write_stdin`、`update_plan`、`request_user_input`、`view_image`、`multi_agent_v1`、`web_search`。`codex exec review` 同样有 `--output-schema`、`--uncommitted`、`--base`。
- **Codex 的大提示**。用户提示 1,048,576 字符会开回合；1,048,577 字符本地退出码 1，`input_too_large`（`max_chars` 1,048,576，JSON-RPC -32602），请求没发出去。1,000,000 字符的提示，头和尾都在请求体里（请求体约 1,060,124 字节，另有约 60 KB 的 instructions）。分段后的每一段都要留在这个上限以内。
- **本机 Codex 服务商**。沿用配置里的模型 `gpt-6-sol`，`codex exec --sandbox read-only --output-schema` 打到 `/v1/responses`，返回 `503`：当前分组 default 下该模型无可用渠道。Codex 会重连（探针 22 秒时停在 2/5），没有写出 `-o`。真实服务商上的结构化输出仍没跑通，请求形状以本地模拟为准。测本地模拟时，系统代理（HTTP/HTTPS/SOCKS `127.0.0.1:7897`）会把回环地址也送进代理，监听端看不到连接、客户端报 502；`NO_PROXY=127.0.0.1,localhost` 后请求到达。正式审阅走用户自己的 https 服务商，不改代理。

## 7. 开源与工程规范

- 许可证：**MIT**（与主要借鉴来源兼容）。仓库公开，包含 README（中英文）、CONTRIBUTING，以及第三方许可证清单 `THIRD_PARTY_NOTICES.md`。
- CI（GitHub Actions）：typecheck · ESLint · Vitest · Playwright（`_electron`）冒烟测试 · electron-builder 打包。
- 发布：推 `v*` tag 后流水线构建 arm64 和 x64 的 dmg + zip，生成 GitHub Release 草稿；应用每 24 h 检查一次新版本并提示。目前是 ad-hoc 签名，Developer ID 签名、公证和自动更新需要作者的 Apple Developer 账号。发版步骤见 [CONTRIBUTING](../CONTRIBUTING.md)。
- 本机自用安装：`npm run app:install` 构建一个“链接版” Wavi.app 放进「应用程序」——只有 Electron 和几行入口，运行本仓库的 `out/`（入口通过 `TR_SOURCE_ROOT` 告诉主进程）。它像正式版一样常驻 Dock、重启后还在；更新只需 `npm run build` 或开着 `npm run build:watch`：renderer 变了自动重新载入（有守护进程时，否则先问），main / preload 变了提示重启（会话由守护进程接回）。链接版保留开发菜单、不检查新版本；挪动或删除仓库后失效，改版本号后重跑一次。`npm run dev` 用单独的 “Wavi Dev” 配置，不会抢正式配置的单实例锁和守护进程。
- 隐私：默认不收集任何遥测数据；崩溃上报为可选项，需用户主动开启。
- 版本：遵循 SemVer，维护 CHANGELOG。
